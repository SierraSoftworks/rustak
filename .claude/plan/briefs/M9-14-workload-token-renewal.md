# M9-14 — A sidecar's workload identity must survive its own renewal (control link dies ~2 h after start)

**Why — production defect, 2026-09-22 (Dublin, Nomad).** About two hours after every sidecar start the control link dies for good: the sidecar logs `Could not exchange this sidecar's workload identity for an access token … The server refused this workload identity (400 Bad Request)` and rustak logs `ERROR … auth.workload.verify: error=Claims` with the full request-header span **every five seconds per sidecar, forever** (137 rustak lines/hour). The feeds keep publishing over the CoT stream; only the control link (Services page, heartbeats, config, events) is dead. Cause: Nomad issues the workload JWT with `ttl = 1h` and **renews it by rewriting the file** `${NOMAD_SECRETS_DIR}/nomad_rustak.jwt`; the environment variable `NOMAD_TOKEN_rustak` is frozen at process start. M9-06's auto-detection order (the orchestrator's own specification, and wrong) is env → file → Kubernetes path, and "re-reads the token on every use" is meaningless for an environment variable. So an hour after start the JWT the sidecar presents has expired; the first access-token expiry (~1 h) is survived once (find out exactly how — rustak logged a single `error=Rejected` per sidecar at ~1h02m with no sidecar-side warning), and the second (~2 h) needs a fresh exchange that can never succeed. The deployment is working around it with `env = false` in the jobspec `identity` block.

**Read first:** `.claude/plan/conventions.md`; status M9-06 (workload identity: `rustak-client/src/sidecar/workload.rs` — source detection, the jwt-bearer exchange, the access-token cache; `rustak-server/src/auth/workload/**` — `verify`, `grant`, rules), M9-07 (`sidecar/link_health.rs`: `Failure::{Unreachable, Refused}` — only transport failures count as "down" and back off), M9-11 (`sidecar/event_feed.rs`, the Identity line's pure renderer, the server's request-log levels in `web/telemetry.rs`); `docs/deployment.md` "Workload identity" (Nomad and Kubernetes reference examples), `docs/plugins.md` credentials section, the three plugins' `config.example.toml`.

**Deliver.**
1. **Source selection that follows renewal.** Auto-detection prefers a **file** source over the environment whenever a file exists (`${NOMAD_SECRETS_DIR}/nomad_rustak.jwt`, then the Kubernetes projected path), because both orchestrators renew by rewriting the file; the environment variable is used only when no file exists. An explicit `[service] workload_identity = { env = … }` is still honoured, with a start-up `warn` saying an environment variable cannot be renewed and naming the file alternative. Every use re-reads the file. Decode the presented JWT's `exp` (unverified, client side, no new dependency if one already in the tree can do it) so the client knows what it is holding: if the token read is already expired or expires within 60 s, re-read once after a short wait (the orchestrator may be mid-rewrite) before presenting it; never present a token the client itself can see is expired when a fresher source exists.
2. **Say which credential and when it expires.** The Identity line names the source actually used and its expiry (`… with the workload identity from /secrets/nomad_rustak.jwt (expires 2026-09-22T05:19:27Z, renewed by the orchestrator)`). When the server refuses and the client can see the presented token was expired, the error says so first (`the workload identity this sidecar presented expired 58m ago; its source NOMAD_TOKEN_rustak is an environment variable, which the orchestrator cannot renew`), ahead of the generic `[auth.workload]` advice.
3. **A refused credential backs off.** Today `Refused` does not count as down, so the exchange is retried every tick (5 s) forever. Keep the distinction in what is *said* (the link is up; the credential is refused), but retry a refused exchange on a capped exponential schedule (5 s → 5 min, reset on success or when the token source's content changes), with `link_health`'s cadence for the log (one warn, debug repeats, five-minute counted reminder, one info on recovery). Heartbeats/events that need the token wait for it rather than each provoking an exchange.
4. **Server: name the claim, quietly.** `auth::workload::verify` must report *which* check failed and by how much, without any token material: `exp: expired 58m12s ago`, `nbf: not valid for another 40s`, `aud: expected "rustak", token names ["vault"]`, `iss: …`, `kid … is not published by issuer nomad`, signature. Log a refusal **once per (issuer, subject, reason) per five minutes** at `warn` with a count on the reminder, never at `ERROR` and never with the request-header span; repeats are `debug`. The `/oauth/token` response stays `400 {"error":"invalid_grant"}` but gains an `error_description` with the same human sentence (it names no secret and the caller is the token's holder). Check the enrolment-route refusal path for the same `err(Debug)`-at-ERROR pattern and treat it the same. Audit entries are unchanged.
5. **The first expiry.** Find out and state in your status note how the sidecar survived the first access-token expiry with an expired workload JWT (a refresh token? a JWT whose `exp` is later than `ttl`? clock skew allowance?) — if rustak accepted an expired assertion anywhere, that is a security bug to fix and test, not a convenience.
6. **Docs and examples.** `docs/deployment.md` Nomad reference: `identity { name = "rustak", aud = ["rustak"], ttl = "1h", file = true, change_mode = "noop" }` with **`env = false`** and a sentence on why (the environment cannot be renewed); Kubernetes reference unchanged in substance (projected volume is a file) but say the same thing; `docs/plugins.md` and the three `config.example.toml`s: detection order and the renewal rule. `.claude/plan/compat/enrollment.md` if it states the order.
7. **Tests.** Client (clock-injected, no sleeps): with both env and file present the file is used; a file rewritten between two uses is picked up (assert the presented token changed); an expired env-only token produces the specific error text and the start-up warn; a refused exchange backs off on the schedule and resets when the file's content changes; the Identity line renders source + expiry. Server: each refusal reason renders its sentence with no token material (assert the token string is absent); repeated refusals produce one warn then debug then a counted reminder (assert on the state machine, not log capture); `error_description` present; an **expired assertion is refused everywhere** (enrolment routes and `/oauth/token`), including one that expired inside the configured `clock_skew` boundary ± 1 s. Integration (`rustak-server/tests/workload_identity.rs` or `sidecar_enrolment.rs`): a sidecar whose file-sourced JWT is replaced by the test issuer mid-run keeps its control link across an access-token expiry (shorten lifetimes through test configuration, not sleeps).

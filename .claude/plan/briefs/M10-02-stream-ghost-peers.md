# M10-02 — Bound how long a vanished peer stays on the stream

**Why.** M9-15 made the server's idle rule `max(last_rx, last_tx)` so that receive-only clients survive. A completed write only proves the bytes reached the kernel, so a phone that drops off the network on a busy channel now stays registered — and shows as connected in contacts — until the send buffer fills and `write_timeout` fires, or the kernel gives up retransmitting (about 15 minutes on Linux defaults). Before M9-15 it was gone in `idle_timeout` (90 s). The stream listener sets `TCP_NODELAY` and nothing else (`rustak-server/src/stream/listener_tls.rs:160`).

**Read first:** `M10-00-wave-rules.md`; brief and status for M9-15; `rustak-server/src/stream/{listener_tls,connection,liveness,writer}.rs`; `rustak-server/src/config/stream.rs`; `config.example.toml` `[stream.tls]`; `docs/deployment.md` stream settings.

**Deliver.**
1. **Socket options on every accepted stream socket**, set beside `TCP_NODELAY`: `SO_KEEPALIVE` with short probes (idle, interval, count) and, on Linux, `TCP_USER_TIMEOUT`, sized from `idle_timeout` so that a peer that has vanished — with or without outbound traffic — is reclaimed in roughly `idle_timeout`, without the server sending a TAK ping. Use safe APIs only (`unsafe_code = "forbid"`): `socket2`'s `SockRef` and `TcpKeepalive` are the expected route; add it through `[workspace.dependencies]` at the current stable version if it is not already a direct dependency. Get the platform facts right and cite them in the rustdoc: what `TCP_USER_TIMEOUT` does to the keepalive probe count on Linux, which keepalive fields exist on macOS and Windows, what happens on a platform with neither. A failure to set an option is logged once at `warn` per listener start, not per connection, and never refuses the connection.
2. **The sizing is a pure function** of `idle_timeout` (its own small module), unit-tested at the default, at a very short and a very long timeout, with sane floors and ceilings. Prefer no new configuration keys; if one is genuinely needed, document it in `config.example.toml` with its default and in `docs/deployment.md`.
3. **The reclaim carries a reason.** When the kernel reports the timeout (`ETIMEDOUT` on read or write), the leave line's `reason` must say so distinctly (`peer_timeout` or the closest existing cause — enumerate what exists in `stream/liveness.rs` and add one only if none fits). M10-01 is changing the end-of-file/reset classification in `liveness.rs`/`connection.rs` at the same time: keep your change there to the smallest addition possible and describe it exactly in your status note so the two can be merged.
4. **Proof.** The backlog asks for a test that blackholes a peer rather than closing it. Find out whether that can be done deterministically in the `Test` job without privileges. If it can, do it. If it cannot, say why, and prove what can be proven: read the options back from a really accepted socket (through the listener's own accept path) on each platform CI runs tests on, and unit-test the `ETIMEDOUT` → reason mapping. Do not add a test that needs root, a firewall rule or a network namespace to the default suite.
5. **Docs.** `docs/deployment.md` and `config.example.toml`: how long a vanished peer can linger and what bounds it, per platform.

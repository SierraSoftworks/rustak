# M9-15 — A quiet client on a busy stream must not be dropped: server idle rule, client keepalive, and a reason on every disconnect

**Why — production finding, 2026-09-22 (Dublin).** rustak closes the FIRMS sidecar's CoT stream every two to four minutes (`The TAK stream went away … reason="the server closed the connection"`; rustak: `A client left the stream. rx=5 tx=305 dropped=0`, no reason given). Only `firms` is affected. Cause, confirmed in the code:
- **Server** (`rustak-server/src/stream/connection.rs::read_loop`): `tokio::time::timeout(deps.limits.idle_timeout, framed.next())` — the idle timeout (`[stream.tls] idle_timeout`, default 90 s) is a **read**-idle timer. It fires when the *client* has sent nothing for 90 s, however much the server is successfully writing to it. The reclaim is logged at `debug` ("went quiet and was reclaimed") and the `info` leave line carries no reason.
- **Client** (`rustak-client/src/stream/keepalive.rs`): ATAK's rule — ping after 15 s of **inbound** silence, repeat every 4.5 s, dead at 25 s; only `record_rx` moves the ping clock. A client that *receives* a steady broadcast (here: AIS and ADS-B tracks relayed to every member of the channel) is never inbound-silent, so it never pings.
- FIRMS has nothing to publish (no fires in Ireland), so it sends nothing at all after negotiation: 90 s later the server drops it. It survives exactly as long as the broadcast happens to leave ≥15 s gaps often enough to provoke a ping (hence the irregular 114–230 s). ESB, AIS and ADS-B publish regularly; CloudTAK and ATAK report their own position, so they never go 90 s without sending — but any receive-only TAK client on a busy server would be dropped the same way, which is a compatibility bug, not just a sidecar one.

**Read first:** `.claude/plan/conventions.md`; `compat/streaming.md` (keepalive: what ATAK sends and when; the server answers a ping with `t-x-c-t-r` to the pinger only); status M1-05/M1-09/M1-10 (stream connection tasks, writer queues, `write_timeout`, drop-then-close, `WRITER_DRAIN`), R-03 robustness review notes on reclaiming dead connections; `rustak-server/src/stream/{connection,writer,hub,metrics}.rs`, `config/stream.rs` (`idle_timeout`, `write_timeout`); `rustak-client/src/stream/{keepalive,connection,reconnect}.rs`; `docs/deployment.md` (stream settings), `config.example.toml` `[stream.tls] idle_timeout`.

**Deliver.**
1. **Server: idle means idle in both directions.** A connection is reclaimed for idleness only when nothing has been **received** from it *and* nothing has been **successfully written** to it for `idle_timeout`. Track the last completed write per connection (the writer task already knows when a flush completes) and measure the idle deadline from `max(last_rx, last_tx)`. A vanished peer under outbound traffic is still reclaimed by the existing `write_timeout` / queue drop-then-close path — verify that with a test and say so in the docs; a vanished peer with no traffic either way is reclaimed by the idle timeout exactly as today (the client would have pinged at 15 s). Do not add a server-initiated ping. Update the `idle_timeout` documentation in `config.example.toml` and `docs/deployment.md` to state the rule precisely.
2. **Server: say why a client left.** The `info` line `A client left the stream.` gains `reason = "idle" | "client_closed" | "read_error" | "write_timeout" | "slow_consumer" | "shutdown" | "revoked" | "replaced"` (use the set of causes that actually exist in the code — enumerate them; each close path must set one) and `connected_for`. Keep it one line per disconnect; add a per-reason counter to `StreamMetrics`. No token or certificate material.
3. **Client SDK: keep a quiet connection alive.** In addition to ATAK's inbound-silence rule, send a ping when the client has **sent** nothing for 30 s (`Keepalive { …, outbound_idle: Duration }`, default 30 s, `OFF` disables it; any frame written resets it, including pings). This keeps every receive-only sidecar alive against any server with a read-idle rule (older rustak builds included), independently of fix 1. The death clock stays keyed on inbound silence. Clock-injected tests in `keepalive.rs`'s existing style: a connection receiving steady traffic and sending nothing pings at 30 s and every 30 s after; sending anything restarts that clock; the inbound rules are unchanged.
4. **Client: `attempts` must not read like a failure count.** `stream::reconnect` logs `attempts=N` that counts every connect for the life of the process, so a healthy reconnect after an hour reads `attempts=17`. Reset the attempt counter on a successful connection (log `attempts` as attempts since the last success) and carry the lifetime figure separately as `connects`. While there: the first failed connect in a process must not say `The TAK stream went away; reconnecting.` — before the first connection has ever been up say `Could not connect to the TAK stream yet; retrying.` (this is already in the backlog; do it here since you are in the file).
5. **Tests.** Server (in-process, fake client built on `rustak-client` with keepalive OFF so the test controls what is sent): a client that sends nothing but is being written to every few seconds is NOT reclaimed after `idle_timeout` (shorten the timeout through test config; no wall-clock upper bounds — assert that the connection is still registered after N relayed messages and a paused-clock advance if the loop allows, otherwise use generous hung-wait timeouts only); a client that neither sends nor receives IS reclaimed and the leave line's reason is `idle`; each other close path sets its reason (client close, read error, revoked certificate, shutdown; write timeout if it can be provoked deterministically — if not, unit-test the reason plumbing and say so). Client: as in item 3, plus the reconnect wording/counter. State in your status note how each new test behaves on a host ten times slower.
6. **Docs.** `docs/deployment.md` and `config.example.toml`: the idle rule; `docs/plugins.md`: the SDK keeps a quiet sidecar's stream alive on its own; `compat/streaming.md`: a note that TAK clients ping on inbound silence only, so a server must not treat read-silence as death while it is writing.

# M10-16 — Would cargo-nextest make the suites faster, and is it worth it on GitHub Actions?

**Why — asked by the maintainer, 2026-09-29.** The `Test` job runs `cargo test --workspace --no-fail-fast` under coverage (grcov) and takes 22–28 minutes; its bound was raised to 90 minutes on 2026-09-22. `cargo test` runs test *binaries* one after another and the tests inside each in parallel threads; nextest runs every test in its own process, in parallel across binaries. Which is faster for this workspace is a measurement, not an opinion. The answer decides whether CI changes.

**This is an evaluation first.** A recommendation of "no" or "only locally" with figures is a complete result.

**Read first:** `M10-00-wave-rules.md`; `docs/ci.md` (the `Test` job's sizing notes and history); `.github/workflows/rust.yml` (`Test` job: toolchain, cache, coverage flags, grcov, the codecov upload; and the comments on why tools are fetched from pinned release assets with SHA-256 rather than `cargo-binstall`); the CI lessons in status notes CI-01/CI-02 and M9-13; brief M10-07 (running at the same time: it makes `workload_identity` and three sibling suites cheaper by sharing one warmed issuer and one server per test binary — read its worktree's diff at `/Users/bpannell/dev/gh/SierraSoftworks/rustak/.claude/worktrees/agent-a3d2658fb91a0e682` read-only if it has got that far).

**Questions to answer, with figures.**
1. **Local wall time**, whole workspace, tests already built (`--no-run` first, so only execution is timed): `cargo test --workspace --no-fail-fast` against `cargo nextest run --workspace --no-fail-fast` plus `cargo test --workspace --doc` (nextest does not run doctests). Other agents are building on this machine, so single figures are noise: interleave the two (A, B, A, B, …), at least three of each, report every figure and the median, and say how loaded the machine was. Repeat with the parallelism a GitHub-hosted runner has (`--test-threads 4` / `-j 4`; check the runner's current core count for public repositories), because the local ten cores flatter both.
2. **Per-binary breakdown**: which binaries gain and which lose. Process-per-test removes anything shared inside a process — a `LazyLock`/`OnceLock` key set, a server shared by a suite — so a suite built on sharing can get *slower*. Name every suite where that happens on main today, and say what M10-07's design would do under nextest. If the best answer is mixed (nextest for most, `cargo test` for named binaries, or nextest test groups / per-test overrides to serialise or pin them), measure that combination too.
3. **Correctness under nextest**: every test that passes under `cargo test` passes under nextest, ten runs in a row; list any that do not and why (tests that depend on running in the same process as another, on ordering, on a fixed port, on the working directory). Such a dependency is a defect in the test whether or not nextest is adopted: list them as findings, fix the ones that are small and inside test code.
4. **Coverage**: does the grcov flow still produce the same coverage with nextest (one `.profraw` per process — check the `LLVM_PROFILE_FILE` pattern, the file count and size on disk, and that the merged report's line totals match `cargo test`'s within noise)? If the job would have to move to `cargo-llvm-cov` to keep working, say so and what that costs.
5. **Cost in CI**: how nextest would be installed following the workflow's existing rule (pinned version, release asset, SHA-256, curl retries, cache in front; no `cargo-binstall`), how long that step takes cold and cached, and what it adds to the Actions cache (the repository has been at its 10 GB limit). Retries: nextest can retry flaky tests — this repository's rule is that a flaky test is fixed, not retried, so retries stay **off**; what nextest does give for free (per-test timing, slow-test reporting, JUnit output, a hung-test timeout that names the test) is worth listing.
6. **Estimate for the `Test` job**: from recent runs' logs (`gh run view`, `gh api …/jobs/<id>/logs`; read-only) take the per-binary times on the runner and project what nextest would do. State the estimate as a range with its assumptions.

**Deliver.**
1. `.claude/plan/status/M10-16-nextest-evaluation.md`: the figures, the findings, and a recommendation — adopt in CI / adopt locally only / do not adopt — with the threshold you used. Setup and maintenance cost counts: a saving of a minute or two on a 25-minute job is not worth a new pinned tool.
2. **If, and only if, the recommendation is to adopt in CI**: the change, ready to land — `.config/nextest.toml` (a `ci` profile: no retries, `fail-fast = false`, slow-timeout set as a generous hung-wait, JUnit output if something will read it), the `Test` job in `.github/workflows/rust.yml` (you may edit this file for this brief), the doctest step, coverage still uploaded, `docs/ci.md` and `CONTRIBUTING.md` updated. The workflow change cannot be proven locally: say exactly what was verified and what only the first CI run can show, and what to compare that run against.
3. If the recommendation is local-only, document it in `CONTRIBUTING.md` and add `.config/nextest.toml`; leave the workflow alone.

# M10-11 — "Why was I refused?" has an answer: the rate limiter's lockouts are visible

**Why — M9-14.** A 15-minute address lockout earned by one process silently refused the next process's first credential exchange, and nothing recorded that it had existed. M9-14 added one throttled `warn` when the limiter refuses a credential. Still missing: a count per class of limiter key, and a way for an administrator to see what is locked out now without reading code.

**Read first:** `M10-00-wave-rules.md`; brief and status for M9-14; R-01 security review's notes on rate limiting (`.claude/plan/reviews/`); `rustak-server/src/auth/ratelimit.rs` and every caller; `rustak-server/src/config/auth.rs`; how other admin read endpoints and their UI pages are built (`rustak-server/src/web/api/`, `rustak-api`, `rustak-ui/src/pages/` — the Services page from M9-03 is a recent example) and how metrics are exposed today (`StreamMetrics`, the OpenTelemetry meters if any).

**Deliver.**
1. **Counters per key class** (address, account, client/credential — enumerate the classes that exist): refusals and lockouts started, exposed the way the server's other metrics are. No key values in metric labels: a label is a class, never an address or a username.
2. **An admin read endpoint** listing current lockouts: key class, the key, when it began, when it ends, how many failures earned it. Administrators only, same authentication and authorisation as the neighbouring admin endpoints, typed in `rustak-api`, contract-tested (status, content type, JSON shape, refusal for a non-administrator). Reading the list must not extend, create or clear a lockout, and must not be rate-limited into uselessness by the lockout it reports. Bound the response size.
3. **An admin action to clear one lockout**, audited (who, which key class and key, when) through the existing audit trail. Clearing is a deliberate act, one key at a time.
4. **Where it shows in the console.** A small table on the page where an administrator already looks at security/authentication state (find the right home; do not add a top-level page for it), with the clear action behind a confirmation. Follow the existing components and the UI test conventions from M7-04; add an e2e spec only if the neighbouring pages have one.
5. **Privacy and safety.** An address or username in a lockout is operational data shown to administrators only; it is not logged at `info` on every read. The limiter's behaviour — thresholds, windows, what earns a lockout — does not change in this brief.
6. **Docs.** `docs/` where authentication and operations are described: what a lockout is, how to see and clear one.

**Files you own:** `rustak-server/src/auth/ratelimit.rs` (split if it grows past the limit), a new admin API module under `rustak-server/src/web/api/`, `rustak-api` types, the UI page/component, tests, docs, your status note. **Not yours:** `rustak-server/src/auth/oauth_server/**` (M10-06), `rustak-server/src/auth/cert.rs` (M10-10), `rustak-server/src/stream/**`. The UI is built with `trunk` outside the Cargo workspace: run the UI's own checks (see `CONTRIBUTING.md` and the `ui` job in `.github/workflows/rust.yml`) in addition to the wave's exit checks.

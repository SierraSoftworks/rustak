# M10-14 — The Profiles view: spaced toggles, and a preferences editor built from a schema

**Why — asked for by the maintainer, 2026-09-29, from the Device profile page in production.**
1. **The toggles under "Delivered" have no margin between them.** `Active`, `On enrolment` and `On connect` are stacked with their switches touching. (The `Channels` toggles on the same card are laid out in a row with gaps and read fine.)
2. **The preferences editor is not laid out consistently.** Each preference is a free-text key, a type select (`String`, …), a free-text value and a `Remove` button on one row, with help text below; `Add a preference` sits directly on top of `Save preferences` / `Revert` with no gap, and nothing tells the operator which keys exist or which values each accepts. The maintainer wants the **same JSON-Schema-based editor controls the Services page uses for plugin configuration**, combined with **a default set of possible options and their valid values**.

**Read first:** `M10-00-wave-rules.md`; status for M3-02 (profiles), M9-03 (Services page) and whichever brief built the schema-driven service configuration form (`git log -- rustak-ui/src/pages/service_config`); `rustak-ui/src/pages/{profiles,profile_editor,profile_delivery,profile_prefs,profile_files}.rs`; `rustak-ui/src/components/{prefs_editor.rs,form/}`; `rustak-ui/src/pages/service_config/{mod,schema,form,inputs,groups,json}.rs`; `rustak-ui/src/pages/panels/display.rs` (the account's own `symbologyProvider` choice); `rustak-server/src/profiles/{catalog,account}.rs` and the profiles API; `rustak-server/tests/profiles_contract.rs`; `e2e/tests/{profiles,preferences,services}.spec.ts`; `.claude/plan/compat/` and `research/` on device profiles and ATAK preference keys and their Java classes.

**Deliver.**
1. **Toggle spacing.** The "Delivered" toggles get the same vertical rhythm as other stacked controls in the console. Fix it in the shared toggle/field-group styling if that is where the fault is, and check every other stacked group of toggles in the console for the same fault (list what you checked). Also give `Add a preference` and the `Save preferences` / `Revert` row proper separation.
2. **One schema-driven form, used by both pages.** Lift the JSON-Schema form controls out of `pages/service_config/` into a shared component module (`components/schema_form/` or similar) that the Services page and the Profiles page both use; the Services page must look and behave exactly as it does today (its e2e specs are the guard). Do not fork the controls.
3. **A catalogue of known preferences, as a schema.** The server already has a preferences catalogue (`rustak-server/src/profiles/catalog.rs`). Extend it, or describe it, as a JSON Schema the UI fetches: for each known key — its title, help text, the Java class ATAK reads it as (`String`, `Boolean`, `Integer`, `Long`, `Float`, … whatever the wire format supports), its valid values (`enum`, ranges, patterns), and ATAK's own default where known. Start with the keys the repository already knows about and those documented in `compat/`/`research/`; every entry must be a fact you can cite from those documents or from ATAK's public documentation — no invented keys, and atak-civ is GPL (facts only, no copied text). A short catalogue that is right beats a long one that is guessed. Serve it from the admin API (typed in `rustak-api`, contract-tested), so the catalogue has one home and the UI does not carry its own copy.
4. **The preferences editor.** Known keys are chosen from the catalogue (searchable; the existing `tree_select` picker may fit) and edited with the control their schema calls for: a select for an `enum`, a toggle for a boolean, a number input with its bounds, text otherwise — each laid out as the Services form lays out a field (label, control, help text, default shown as the placeholder or hint). The Java class comes from the catalogue and is not asked for. **Unknown keys stay possible**: an "other preference" row keeps key, class and value free, because ATAK plugins define keys the catalogue cannot know; it is laid out in the same grid as the rest. Existing stored preferences that are not in the catalogue, or whose stored class or value disagrees with it, are shown and preserved exactly — never silently rewritten or dropped — with a note where they disagree. Delivery order is preserved and remains editable if it is today.
5. **What is sent to devices does not change.** The profile package's preference XML for a given stored profile is byte-identical before and after (the contract tests are the guard; add one for a profile holding a catalogue key, a free key and a disagreeing value).
6. **Tests.** Component tests in the UI's existing style (M7-04); e2e: add or update `profiles.spec.ts` to choose a known preference, set it through its control, save, reload and see it; and to add a free key. Keep `services.spec.ts` green untouched unless a selector genuinely moved.
7. **Small screens.** The page works at the widths `small-screens.spec.ts` covers.

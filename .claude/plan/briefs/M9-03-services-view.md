# M9-03 — A working Services page in the admin console

**Why.** The maintainer's instruction (2026-09-20): "make sure the Services view is actually working, so that we can monitor the state of these plugins (and potentially configure them if needed)." The server side exists since M6-01 — `GET /api/v1/services`, `POST /services/register`, `DELETE /services/{name}`, `POST /services/{name}/heartbeat`, `GET|PUT /services/{name}/config`, with `ServiceSummary { id, descriptor { name, display_name, version, capabilities, endpoints }, status { state, message, last_heartbeat_at }, registered_at, metrics }` — but the admin UI's page is still the `AddOns` stub in `rustak-ui/src/pages/stubs.rs` ("Arrives in M6"), and `docs/plugins.md` already promises that heartbeat `metrics` are "rendered in the admin UI as-is". Make that true, in time for the AIS and ADS-B plugins (M9-01/M9-02, in flight) which will report feed counters and source state in their heartbeats.

**Read first:** `.claude/plan/conventions.md`; status M6-01 (services API, registry, health sweep, per-service config rules: a service reads only its own config, only an administrator writes it), M3-04 and M2-07 (UI patterns: pages, panels, `api/` clients, demo fixtures via the `?demo` macro, `confirm`, `secret_reveal`, tables, the drawer), M7-04 (demo flags such as `?demo&tls=`); `rustak-api/src/service.rs`; `rustak-server/src/web/api/services.rs` and `plugins/{registry,health}.rs`; `rustak-ui/src/pages/{clients,devices,dashboard}.rs` as the closest existing list/detail pages; `rustak-ui/src/pages/stubs.rs`; `e2e/tests/{navigation,identity}.spec.ts` for the Playwright conventions; `docs/plugins.md` → "Registering with the server".

**Deliver.**
1. **Services list page** replacing the stub at the existing "Services"/"Add-ons" route (keep the navigation entry's path; rename the label to "Services" if it says Add-ons): one row per registered service — display name (and `name`), version, state pill (`healthy` / `degraded` / `unhealthy` / anything `ServiceState` has, using `needs_attention()` for emphasis), status message, last heartbeat as relative time with the absolute on hover, registered-at, capabilities as small tags. Sort attention-needing services first. Empty state that explains how a sidecar registers (one sentence and a link to the docs page). Refresh every 10 s while the page is visible (no SSE work); a manual refresh button.
2. **Service detail** (drawer or page, following what `clients.rs`/`devices.rs` do): everything above, plus the descriptor's endpoints and the heartbeat **`metrics` rendered as a key/value table** for flat objects, nested objects indented one level, arrays as comma-joined — never raw JSON unless the value is not an object, and never HTML-interpret a string. A **Configuration** panel that `GET`s `/services/{name}/config` and lets an administrator edit it as JSON (a textarea with validation on save, "changed since load" guard) and `PUT`s it back, with the note the docs make: the service reads it on its next tick. A **Remove** action (`DELETE`, confirm dialog) for a service that has gone away. Add-only server changes are allowed if a field the page needs is missing — e.g. if `GET /services/{name}/config` refuses administrators today, fix the authorization so admins can read as well as write (the M6-01 rule is "service reads only its own; admin writes" — admin *reading* is implied by writing), with a test.
3. **Dashboard tile** (if `dashboard.rs` has a tile grid): a count of services and how many need attention, linking to the page. Skip if the dashboard has no such pattern.
4. **Demo fixtures** (`?demo`): three services — a healthy `rustak-plugin-ais` with feed-shaped metrics (`offered`, `published`, `suppressed`, `expired`, `tracked`, `source: { kind: "aisstream", state: "connected" }`), a degraded `rustak-plugin-adsb` with a message and a `source.state: "reconnecting"`, and an unhealthy `rustak-plugin-example` whose last heartbeat is old — plus a config object for one of them. Fixture mutations for save/remove.
5. **Tests**: rustak-ui unit tests for the metrics renderer (flat, nested, array, non-object, string with markup stays text) and the relative-time helper; Playwright `e2e/tests/services.spec.ts` against `?demo`: the list renders three rows with the right pills and ordering, the detail shows the metrics table and endpoints, editing the config and saving shows the saved state, removing a service removes its row, and the navigation spec still passes. Server: a route test that an administrator can `GET` a service's config and a non-admin cannot, if you touched authorization.
6. **Docs**: `docs/plugins.md` — a short "Monitoring a sidecar" subsection (what the page shows, what `metrics` should look like to render well: flat keys, numbers, short strings), and make the existing "rendered in the admin UI as-is" sentence accurate. `README.md`: no change unless the highlights mention the admin UI's pages.

No `git`/`but` writes. Files < 300 functional lines.

# M0-18 — Fix the two defects the e2e harness found (wizard CA step, resident passkeys)

**Defects (from `.claude/plan/status/M0-14-e2e-specs.md`):**
1. `runtime` creates the root CA before the listener binds, so `POST /api/v1/setup/ca` always returns 409 on a fresh install and the linear wizard dead-ends. Fix: make the CA step idempotent — if a CA already exists, `POST /setup/ca` returns 200 with the existing `CaSummary` (and `GET /setup/status.has_ca` stays true); the UI's CA step shows the existing CA (subject, fingerprint, validity, download link) with "Continue" instead of a create form when `has_ca` is true. Keep the create path for the case where no CA exists (e.g. `[pki]` disabled in future).
2. Passkey registration requests `residentKey: "discouraged"` while the login UI only performs a discoverable (`allowCredentials` empty) ceremony, so a freshly registered passkey cannot sign in. Fix: register with `residentKey: "required"` (fall back to `preferred` only if `webauthn-rs` cannot express `required`) and `userVerification: "preferred"`; keep the discoverable login as the primary flow and add a username-assisted fallback (`login/start` accepts an optional `username` and returns `allowCredentials` for that user) so non-resident keys from other authenticators still work. Update the passkey compat docs in `docs/deployment.md` (one paragraph) if behaviour changes for users.
3. Then delete the corresponding work-arounds in `e2e/tests/{setup.spec.ts,helpers.ts,webauthn.ts}` (the 409-reload path and the CDP resident-key conversion) so the specs assert the fixed behaviour, and add a spec that registers a passkey and signs in without any CDP tricks.

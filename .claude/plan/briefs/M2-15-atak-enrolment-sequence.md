# M2-15 — ATAK's real enrolment sequence: profile fetch after the one-time token is spent, and the first handshake

**What happened (real ATAK 5.6, 2026-09-19 08:30 UTC, server logs in `.claude/plan/status/M2-15-field-report.md`).** ATAK enrols in three Basic-authenticated calls with the *same* one-time token: `GET /Marti/api/tls/config` → `POST /Marti/api/tls/signClient/v2` → `GET /Marti/api/tls/profile/enrollment?clientUid=`. rustak spends the token on the successful sign (by design, M2-03/M5-02), so the third call answered `401` (`identity::verify: error=BadSecret`, then `auth::basic: error=Rejected`). ATAK showed "Failed to get profile: Enrollment (401)" and "TAK server registration failed", then "Read error: ssl=…: Failure in SSL library, usually a protocol error" on its first stream attempt, and connected about a minute later. The commoncommo harness never caught this because `estream:` does not fetch the enrolment profile (M1-00 matrix: device profiles are ATAK-Java).

**Read first:** `.claude/plan/conventions.md`; research `07` §1–§2 (the exact enrolment sequence and what ATAK does on each failure), `compat/enrollment.md`, `compat/profiles.md`; `rustak-server/src/marti/{tls,enroll,profiles}.rs`, `identity/{verify,credentials}.rs`, `auth/{resolve,basic}.rs`, `pki/{revoke,tls/client_verifier,tls/peer}.rs`, `stream/resolver.rs`; status M2-03, M3-02, M5-02 (atomic spend), M2-12.

**Deliver.**
1. **Grace window after a successful sign.** A spent enrolment token stays valid for `GET /Marti/api/tls/profile/enrollment` and `GET /Marti/api/tls/profile/tool/**` **only**, for the same `clientUid` it was spent by, for `[auth] enrollment_grace` (default 10 minutes) — nothing else (no second `signClient`, no `/oauth/token`). Record the spend with the client uid and time; the verify path distinguishes "spent, in grace, same uid, profile route" from "spent". Negative tests: a second sign with the spent token is refused; the profile fetch from a different uid is refused; after the window it is refused.
2. **The first stream handshake.** Establish why the handshake right after issuance failed and succeeded a minute later. Leading hypothesis: the known-certificate/revocation cache the client verifier consults is refreshed on an interval rather than updated on issuance, so a certificate issued seconds earlier is refused as unknown (`require_known_cert`). If so, insert the issued certificate into the cache in the same transaction/commit as issuance (as revocation already updates it), with a test: issue → immediate mTLS handshake succeeds. If the hypothesis is wrong, find the real cause from the listener's logs (`stream/listener_tls.rs`, `pki/tls/client_verifier.rs`) and fix that.
3. **Log noise:** `identity::credentials: Ignored an ordinary use recorded against a one-time credential` fires at WARN on every `tls/config` call — the expected path. Make it `debug`, or stop recording the use for one-time credentials there.
4. **Coverage:** a contract test in `tests/enroll_flows.rs` that walks ATAK's exact three-call sequence with one token and asserts 200/200/(200|204); extend the node-tak suite's enrolment scenario to fetch the enrolment profile with the same credential (that suite runs on every push). Update `compat/enrollment.md` and `docs/compat/atak.md` (step: after enrolment ATAK fetches the profile with the same token; expected: no 401).
5. **Field report:** write `.claude/plan/status/M2-15-field-report.md` first, quoting the log excerpt below verbatim, so the sequence is on record.

Log excerpt (from the maintainer's server): `tls/config` → WARN "Ignored an ordinary use recorded against a one-time credential. credential=1 kind=enrollment_token"; `signClient/v2` → same WARN, then "Saw a device for the first time. device=ANDROID-7e0bf5df978a87d8", then "Issued a client certificate. subject=CN=notheotherben,O=rustak,OU=rustak … key=RSA-4096"; 0.4 s later `GET /Marti/api/tls/profile/enrollment?clientUid=ANDROID-…` → `identity::verify: error=BadSecret`, `auth::basic: error=Rejected` (401).

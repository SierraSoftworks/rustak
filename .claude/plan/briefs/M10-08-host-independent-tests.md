# M10-08 — The last tests that depend on how fast the host is

**Why.** M9-13's audit flagged two groups and left them untouched; `36f22293` later widened the second group's margins, which makes a failure rarer without removing the cause.
- The `until(EXPECT)` loops and every `expect_uid(.., EXPECT)` in `rustak-server/tests/` allow `EXPECT` = 5 s (`rustak-server/tests/stream_support/mod.rs:31`); in `feed_sidecars` that is measured from sidecar spawn across register, handshake and first tick. They passed on the slowest CI run seen but are next to fail if runners slow further.
- The server-event feed's timeout tests in `rustak-client/src/control/events.rs` use **real** timers (hundreds of milliseconds to 1.6 s against real loopback sockets), so a scheduling stall of that size fails them.

**Read first:** `M10-00-wave-rules.md`; brief and status for M9-13 and M9-11; commit `36f22293` (`git show 36f22293`); `rustak-server/tests/stream_support/mod.rs`, `rustak-server/tests/feed_support/mod.rs`, `rustak-server/tests/feed_sidecars.rs`; `rustak-client/src/control/events.rs` tests.

**Deliver.**
1. **`EXPECT` is a hung-wait, so make it one.** Raise it to a value no healthy host reaches (60 s is the expected order) everywhere it means "wait for something that will come"; a passing test returns as soon as the thing arrives, so this costs nothing when green. Audit every use: where `EXPECT` was really being used as an upper bound on something that should *not* happen, or to assert promptness, replace the assertion with a count, an order or a state. `SETTLE` (the negative wait) stays short, but check each use is a genuine negative assertion whose positive path cannot be slowed by the host into a false pass; list any you doubt.
2. **The event-feed timeout tests stop depending on real time.** Put them on a clock the test controls. `tokio::time::pause` with real sockets auto-advances whenever the runtime is idle, which can fire a timeout before loopback I/O is delivered — so decide deliberately: either drive the feed over an in-memory transport (a duplex stream or a stub `Stream` of bytes) under a paused clock, or inject the timeout so the test asserts *which* timer fired and in what order rather than how long it took. The reqwest client's own `read_timeout`/`connect_timeout` run on tokio timers; find out whether they honour a paused clock before relying on it. What must remain proven: a silent feed is declared dead after the idle timeout; keep-alive comments keep a silent feed open; there is no total timeout; the connect timeout bounds opening.
3. **State for every changed test how it behaves on a host ten times slower**, in the status note, and run each changed suite at least ten times in a row, and once under load (`CARGO_BUILD_JOBS=4 cargo build` of something else running beside it), reporting the counts.

**Files you own:** `rustak-server/tests/stream_support/mod.rs`, `rustak-server/tests/feed_support/mod.rs`, `rustak-server/tests/feed_sidecars.rs`, other `rustak-server/tests/*.rs` only where an `EXPECT` use has to change meaning, the tests in `rustak-client/src/control/events.rs` (production code there only if a timeout has to become injectable, and then additively), your status note. **Not yours:** `rustak-server/tests/{workload_identity,sidecar_enrolment,sidecar_trust,hostile_server_name}.rs` (M10-07) — if an `EXPECT` use in those needs more than the constant's new value, name it in the status note instead of editing.

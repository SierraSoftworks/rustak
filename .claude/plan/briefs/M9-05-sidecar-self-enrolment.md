# M9-05 — A sidecar enrols its own certificate from a one-time enrolment token

**Why.** `docs/plugins.md` says "a sidecar enrols when it has no certificate rather than on every start" and shows `rustak_client::enroll`, but the harness (`rustak-client/src/sidecar/**`) never calls it: a deployment must produce PEM files some other way, and rustak offers no CLI for that (config packages refuse to include a client key by design; the CloudTAK onboarding bundle is a passphrase-protected PKCS#12 for CloudTAK). The AIS and ADS-B plugins are being deployed to the maintainer's Nomad cluster now, so the promised behaviour has to exist.

**Read first:** `.claude/plan/conventions.md`; `docs/plugins.md` (identity model, credentials, "Two credentials", running one); `rustak-client/src/{enroll.rs,sidecar/{config,run,mod,link}.rs}`; status M6-01 and M1-07 (harness start-up order: env file → telemetry → shutdown → config → stream → start); `compat/enrollment.md` (the `tls/config` → `signClient/v2` sequence, one-time token semantics; M2-15's grace); `rustak-server/tests/{services_flow,enroll_flows}.rs` and `tests/feed_support/mod.rs`; the two plugins' `config.example.toml` `[service]` blocks.

**Deliver.**
1. **Self-enrolment in the harness.** When `[service] certificate`/`key` name files that do not exist (or are unset) *and* `RUSTAK_ENROLLMENT_TOKEN` is set (or `[service] enrollment_token = "${{ env.… }}"`, same `Secret` handling as the service token), the harness enrols before opening the stream: `enroll()` against the Marti/enrolment surface derived from `[server] control` (the public listener serves `/Marti/api/tls/*`; `[server] marti` if such a key exists takes precedence — read the config), with `username` = the service account's name (`[service] account` if that exists, else the service name — read how the descriptor derives `SERVICE-<name>` and keep them consistent), `client_uid = SERVICE-<name>`, then writes the certificate, key and truststore PEMs to the configured paths (or to a `[service] pki_dir`, default beside the config file) with `0600` on the key, logs the certificate's subject and expiry at `info`, and continues start-up with them. On the next start the files exist and no token is needed. A token present while files exist is ignored with an `info` line, so a leftover env var never re-enrols. Enrolment failure is fatal at start-up with a `Kind::User` message naming the cause (bad token, unreachable server, refused CN) — a sidecar must not run half-identified.
2. **Truststore.** rustak's `internal` mode signs with its own CA; the enrolment response's CA chain is what the sidecar must trust for the stream and Marti, so write it as the truststore and use it, unless `[service] truststore` was given explicitly. The public listener's certificate (Let's Encrypt in the maintainer's deployment, or internal CA) is verified with the platform roots for the enrolment call itself, with `[service] truststore` as the override.
3. **`--enroll` flag** on the harness's CLI: perform step 1 and exit 0 without starting the sidecar (for an init container or a one-off task), printing the paths written. `--check` keeps validating without touching the network.
4. **Tests.** `rustak-server/tests/services_flow.rs` (or a new `sidecar_enrolment.rs`): a service account with a minted enrolment token; the harness started with no PEMs and the token in the environment enrols, writes the three files, connects to the stream and registers; a second start without the token uses the files; a wrong token fails with the user-facing message; `--enroll` writes the files and exits. Unit tests on the path/permission handling.
5. **Docs.** `docs/plugins.md` "Two credentials" and "Running one" (the env var, the flag, the first-start story), the two plugins' `config.example.toml` (`enrollment_token` line beside `token`), `docs/deployment.md` "The sidecar images" (the `docker run` example gains `-e RUSTAK_ENROLLMENT_TOKEN` for the first start). Say plainly in the docs that the key is generated inside the sidecar's process and never leaves it.

# M9-06 — Enrol and authenticate a sidecar with its orchestrator's workload identity (Nomad, Kubernetes)

**Why.** The maintainer's decision (2026-09-20): plugins running under Nomad or Kubernetes should enrol with the orchestrator's **workload identity JWT** instead of a one-time enrolment token, so a deployment holds no rustak secret at all; the enrolment token (M9-05) stays for deployments without workload identity. The first production use is the Dublin AIS/ADS-B deployment on Nomad, which is waiting on this — the packs already carry an `identity { name = "rustak", aud = ["rustak"], ttl = "1h", file = true, env = true }` block per task. Deliver Nomad first-class with a Kubernetes issuer of the same shape, and reference examples for both.

**Read first:** `.claude/plan/conventions.md`; `plan.md` → Identity & auth model; status **M9-05** (self-enrolment: `enrolment.rs`, `[service] pki_dir`/`account`/`enrollment_token`, `--enroll`, the "will enrol" `--check`), M6-01 (service tokens, `Purpose::ServiceApi`), M5-01 and M8-01 (`web/helpers/oidc/{validate,discovery,claims}.rs` — JWKS fetch and JWT validation you can reuse; `auth/jwt/keys.rs`), M2-03/M2-15 (the enrolment surface: `marti/{tls,enroll}.rs`, `auth/{basic,resolve}.rs`, `identity/verify.rs` `Purpose`), `auth/acl.rs` (the `filt_rs` claims-expression engine behind `user_acl`/`admin_acl` — check which operators it offers before promising prefix matching); `rustak-client/src/{enroll.rs,sidecar/**}`; `docs/plugins.md`, `docs/deployment.md`.

**Orchestrator facts (verified 2026-09-20 from the vendors' docs; re-check anything you build on):**
- *Nomad*: a jobspec `identity { name, aud, ttl, env, file, filepath, change_mode }` block gives the task a JWT signed by the Nomad servers; a named identity `rustak` is exposed as env `NOMAD_TOKEN_rustak` and file `${NOMAD_SECRETS_DIR}/nomad_rustak.jwt` (default identity: `NOMAD_TOKEN`, `secrets/nomad_token`); the client renews it at about half the TTL. Claims: `nomad_namespace`, `nomad_job_id`, `nomad_allocation_id`, `nomad_task`, plus standard `sub` (`<region>:<namespace>:<job>:<group>:<task>:<identity>` — verify), `aud`, `iat`, `nbf`, `exp`, `jti`; `iss` is present only when the server's `oidc_issuer` is configured. The servers publish the verification keys at `/.well-known/jwks.json` on the HTTP API (verify path and that it needs no ACL token) and, with `oidc_issuer`, `/.well-known/openid-configuration`. Signing: the maintainer's Nomad (2.0.x) discovery document lists `RS256` and `EdDSA` and currently serves six keys that rotate — cache the set and refresh on an unknown `kid`. Confirmed claims from that cluster: `sub` = `global:default:<job>:<group>:<task>:<identity>` (e.g. `global:default:rustak-plugin-ais:sidecar:ais:rustak`), `nomad_namespace` = `default`, `nomad_job_id`, `nomad_task`, `nomad_allocation_id`, `aud`, `iat`, `nbf`, `exp`, `jti`, and `iss` = `https://nomad.raptor-perch.ts.net` because `oidc_issuer` is set there.
- *Kubernetes*: a `serviceAccountToken` projected volume (`audience`, `expirationSeconds` ≥ 600, `path`) gives the pod a JWT rotated by the kubelet; claims `iss` (the API server's `--service-account-issuer`), `sub` = `system:serviceaccount:<namespace>:<name>`, `aud`, and a `kubernetes.io` object with `namespace`, `pod.name`, `pod.uid`, `serviceaccount.name`, `serviceaccount.uid`; discovery at the API server's `/.well-known/openid-configuration` and `/openid/v1/jwks`, readable anonymously only with a binding to the `system:service-account-issuer-discovery` ClusterRole.

**Deliver.**
1. **Server: `[auth.workload]`** — a list of issuers, each `{ name, jwks_url? | discovery_url? | jwks_file?, issuer? (required when the token carries `iss`; absent allowed only for Nomad without `oidc_issuer`), audience (required), algorithms (default RS256/ES256/EdDSA per what each orchestrator signs with), clock_skew = "30s", jwks_refresh = "1h" (refresh on an unknown `kid` at most once a minute) }` and **binding rules**: `{ issuer, namespace_claim = "nomad_namespace" | "kubernetes.io.namespace", namespace, subject_claim = "nomad_job_id" | "kubernetes.io.serviceaccount.name", subject_prefix, account = "strip-prefix" | "<fixed name>", match? = <filt_rs expression over claims, optional extra constraint> }`. A token maps to exactly one account or is refused; a rule for a fixed account is allowed (one job → one account); the **reference rule** is: namespace equals, subject starts with `rustak-plugin-`, account is the remainder (`rustak-plugin-ais` → `ais`). Refuse at `--check`: no audience, a prefix rule with an empty prefix, two rules that could map one token to two accounts (same issuer, overlapping constraints — detect the obvious cases, document the rest), a `jwks_url` over plain `http://` to a non-loopback host unless the issuer sets `allow_insecure_jwks = true`, which logs a warning at every start-up — the first deployment fetches the JWKS from the Nomad server's plain-HTTP API on the same node's tailnet address because the TLS-terminated tailnet name hairpins unreliably from containers there, so `issuer` (the `iss` string to check) and `jwks_url` (where to fetch keys) must be independent settings.
2. **Server: the assertion as a credential.** On the enrolment routes (`Purpose::Enrollment`/`EnrollmentProfile`) and on `POST /oauth/token`, accept `Authorization: Bearer <workload JWT>` (and, for the enrolment routes, Basic with the account as username and the JWT as password, because that is how `commoncommo`-shaped clients send it — keep both): validate signature against the issuer's JWKS, `iss`/`aud`/`exp`/`nbf`/`iat` with skew, apply the rules, load the account (must exist, be kind `service`, be enabled, pass `user_acl`), then behave exactly as an enrolment token would: `tls/config`, `signClient/v2` issues a certificate to the account with `issued_via = 'workload_identity'` and the issuer name, `profile/enrollment` answers. **Re-enrolment policy**: a valid assertion may enrol whenever the workload has no certificate; with `[auth.workload] revoke_previous = true` (default) the account's earlier `workload_identity` certificates are revoked when a new one is issued (audit `certificate.superseded`), so a rescheduled task never leaves a live certificate on old storage. Rate-limit by account like every credential endpoint. Audit `enrollment.workload` with issuer, namespace, subject, `jti` (never the token). `POST /oauth/token` gains `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer` with `assertion=<JWT>` (RFC 7523 §2.1) answering a rustak access token with the service scope (`tokens::SCOPE_API`, or whatever a service token yields today) — this replaces the service token for the control API; response shape as the password grant (`access_token`, `token_type`, `expires_in`), errors `invalid_grant`. The password grant stays byte-identical.
3. **Sidecar: identity source.** `[service] workload_identity = { env = "NOMAD_TOKEN_rustak" } | { file = "…" }` with auto-detection when unset: `NOMAD_TOKEN_rustak` env, then `${NOMAD_SECRETS_DIR}/nomad_rustak.jwt`, then `/var/run/secrets/tokens/rustak` (Kubernetes projected path by convention), logged at `info` which one was found, and — the one line an operator will grep for when a first run misbehaves — after enrolment or token exchange, one `info` line naming the identity source used (`NOMAD_TOKEN_rustak`, a file path, an enrolment token, or existing PEMs), the issuer, and the account rustak bound it to (from the certificate's CN or the token's `sub`). The token is re-read from its source every time it is used (both orchestrators rotate it). Precedence when several credentials exist: files in `pki_dir` → no enrolment; else workload identity → enrol with it (M9-05's flow, presenting the JWT); else enrollment token; else the M9-05 error. For the control API: `[service] token` if set, else exchange the workload JWT at `/oauth/token` (jwt-bearer) and cache the access token until 60 s before `expires_in`, re-exchanging on `401`. `--check` reports which identity source will be used ("will enrol into '/data' with the workload identity from NOMAD_TOKEN_rustak") without reading the network; `--enroll` works with it.
4. **Tests.** Server: a fake issuer in `testing/` (generate an RSA key, serve a JWKS over `wiremock` or the in-process test server, mint JWTs with chosen claims) and `rustak-server/tests/workload_identity.rs`: enrol with a Nomad-shaped token through `tls/config` → `signClient/v2` → mTLS probe; a Kubernetes-shaped token with the nested `kubernetes.io` claims; the reference prefix rule maps `rustak-plugin-ais` to `ais`; refusals — wrong audience, expired, unknown `kid` (then refreshed JWKS accepts), wrong namespace, subject outside the prefix, account of kind `person`, disabled account, tampered signature, `iss` mismatch; re-enrolment revokes the previous certificate and the old cert fails the handshake; jwt-bearer at `/oauth/token` yields a token that reaches `/api/v1/services/*` and nothing more; the password grant response unchanged. Sidecar: `rustak-server/tests/sidecar_enrolment.rs` gains the workload path (env source, file source, rotation between two uses, precedence over a leftover enrolment token, `--check` wording).
5. **Docs and reference examples.** `docs/deployment.md`: a "Workload identity" section with (a) the **Nomad reference**: the jobspec `identity` block, the rustak `[auth.workload]` block with the Nomad issuer (`jwks_url = "https://<nomad-server>:4646/.well-known/jwks.json"`, `audience = "rustak"`, the namespace + `rustak-plugin-` prefix rule — this is the "reference ACL" the maintainer asked for), and a note that Nomad ACLs do not filter by job name, so the rule's namespace is the boundary an operator controls with Nomad's `submit-job` capability (Sentinel is Enterprise); (b) the **Kubernetes reference**: the projected-volume snippet, the discovery-role binding, the issuer block and the namespace + service-account prefix rule; (c) how to hand over an existing deployment from enrolment tokens (nothing to do: PEMs persist). `docs/plugins.md` "Two credentials" becomes "Three credentials". `config.example.toml` documents `[auth.workload]`; the three plugins' `config.example.toml` document `workload_identity`. `compat/enrollment.md`: a paragraph on the assertion credential.

# M10-12 — Deploying a plugin is one console step: service-account onboarding

**Why — suggested by the cluster deployment session while packaging the feed plugins.** Deploying a sidecar that does not use workload identity takes three admin actions today: create the service account, mint its credential, mint a one-time enrolment token. Enrolment tokens expire in 15 minutes (`[auth] enrollment_token_ttl`, server-wide), which is what makes a combined action worth having. M5-03 (CloudTAK onboarding) is the shape to follow: one admin-only, audited action whose secrets are shown once.

**Read first:** `M10-00-wave-rules.md`; briefs and status for M5-03, M6-01, M9-05 and M9-06; how service accounts, service tokens and enrolment tokens are created today (`rustak-server/src/web/api/`, the identity/credentials modules) and what the sidecar needs from each (`rustak-client/src/sidecar/{config,enrolment}.rs`, `docs/plugins.md` deployment section); the Services page (M9-03) and the Users page in `rustak-ui`.

**Deliver.**
1. **One admin action** — `POST` on the admin API, typed in `rustak-api` — that, atomically: creates the service account if it does not exist (refusing a name that belongs to a person's account), and mints a one-time enrolment token for it. Decide from the code whether a service token is still needed by a sidecar that enrols (M9-06's jwt-bearer grant replaced service tokens for workload identities; M9-05's self-enrolment may or may not need one for the control link) and mint one only if a sidecar deployed this way cannot work without it — say what you found. If any step fails, nothing is left behind.
2. **Secrets are shown once**: returned in the response to the action and never retrievable again; stored only as the existing credential stores keep them (hashed or sealed per conventions). The response also carries what an operator pastes into a deployment: the `[service]` configuration fragment and the `RUSTAK_ENROLLMENT_TOKEN` environment line, with the expiry stated.
3. **Audited and rate-limited** like the neighbouring credential-minting actions; administrators only. Repeating the action for an existing service account mints a fresh enrolment token and says that it did; it does not silently revoke what is in use — if re-issuing a credential would revoke a live one, require an explicit flag and say so in the response.
4. **Console.** An "Add a service" action on the Services page: name → result panel showing the secrets and fragment once, with copy buttons and the expiry. Follow M5-03's panel and the UI test conventions from M7-04; add an e2e spec beside the existing Services specs.
5. **Tests.** Contract tests (status, JSON shape, refusals: non-administrator, a person's account name, invalid name); atomicity (a failure in the second step leaves no account); an end-to-end harness test in which a sidecar enrols with exactly what the action returned.
6. **Docs.** `docs/plugins.md` deployment section: the one-step path first, the manual steps after it.

**Files you own:** a new admin API module and its service-layer function in `rustak-server`, `rustak-api` types, `rustak-ui` Services page additions, tests, e2e spec, docs (deployment section of `docs/plugins.md` only), your status note. **Not yours:** `rustak-server/src/auth/{oauth_server,ratelimit,cert}*`, `rustak-server/src/stream/**`, `rustak-client/**` (read only). The UI is built with `trunk` outside the Cargo workspace: run the UI's own checks (see `CONTRIBUTING.md` and the `ui` job in `.github/workflows/rust.yml`) in addition to the wave's exit checks.

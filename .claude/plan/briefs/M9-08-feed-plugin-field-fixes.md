# M9-08 — Feed plugin fixes from the first live run (adsb.lol rate limit, quiet logs)

**Why — production findings, 2026-09-21 (Dublin deployment).** `rustak-plugin-adsb` against adsb.lol at the documented/default `poll = "5s"` received `429` with `Retry-After: 10` on roughly every other request (twelve "asked us to wait" notices in five minutes); the deployment now runs `poll = "10s"`. The notice is logged on every 429. The operator retired a previous TAK server partly for log noise, so the feed plugins must log on state change, not per event. (The control-link half of the noise is fixed in M9-07; this brief is the plugins' own logging and the aggregator cadence.) **Launch only after M9-07 has landed** — both touch `rustak-plugin-*/config.example.toml`.

**Read first:** `.claude/plan/conventions.md`; status M9-02 (`sources/{aggregator,state}.rs`, `SourceState` — already the single place that logs a state change), M9-01 (AIS sources and its status reporting), M9-04 (health hook), M9-07 (control-link state-change logging — match its wording and cadence); `rustak-plugin-adsb/{README.md,config.example.toml,src/settings.rs,src/sources/**}`; `rustak-plugin-ais/src/sources/**`.

**Deliver.**
1. **Aggregator cadence.** Per-provider default poll: `adsb_lol` 10 s (observed `Retry-After: 10`), `adsb_fi` 5 s (documented 1 request/s; keep a polite margin), `airplanes_live` 10 s (unverified, be conservative); an explicit `poll` still wins but is clamped to a provider floor of 2 s with an `info` line when clamped. **Adapt to the server**: when a provider answers `429` with `Retry-After: N`, wait N and, if that happens twice within ten polls, raise the effective interval to `max(current, N)` for the rest of the process and say so **once** at `info` ("adsb.lol asks for 10s between requests; polling at that rate from now on"); never lower it again until restart. The heartbeat metrics gain `source.poll_effective_s` and `source.rate_limited` (count).
2. **Log on state change.** The rate-limit notice, source reconnect warnings and parse-skip notices in both plugins: first occurrence at `warn`/`info` with the cause, repeats at `debug`, at most one reminder every 5 minutes with a count ("adsb.lol rate-limited 23 times in the last 5m"), and one `info` on recovery. Audit both plugins' `sources/**` for any `warn!`/`info!` inside a per-message or per-poll loop and move it behind `SourceState` (ADS-B) or its AIS equivalent. The periodic "The feed is publishing" counters line stays at `info` every 5 minutes.
3. **Docs.** ADS-B README and `config.example.toml`: the per-provider defaults, adsb.lol's observed limit, the adaptive behaviour; remove "one request a second" where it reads as a recommendation. AIS README: nothing unless you changed behaviour.
4. **Tests.** `wiremock`: two `429 Retry-After: 10` within ten polls raises the effective interval and logs once (assert via the state machine, not log capture, unless the crate already captures logs); an explicit `poll = "1s"` is clamped; the metrics carry the two new fields; the reminder cadence with a controllable clock.
5. **If the orchestrator appends AIS findings below before launch, handle them too.**

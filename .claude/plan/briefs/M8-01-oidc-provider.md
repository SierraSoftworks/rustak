# M8-01 — rustak as an OpenID Connect provider (so CloudTAK's SSO can point at rustak)

**Why.** CloudTAK's forthcoming SSO (upstream issue dfpc-coe/CloudTAK#661; TAK.NZ's fork has it in production) makes CloudTAK an OIDC *relying party*: it fetches a discovery document, sends the browser to `authorization_endpoint`, exchanges the code at `token_endpoint` with `client_id` + `client_secret` (`client_secret_post`, **no PKCE**), reads `userinfo_endpoint` (`preferred_username` first, then `email`, plus a `groups` array), and then enrols a TAK certificate with the **access token as a Bearer** on `/Marti/api/tls/config` and `/Marti/api/tls/signClient/v2`. The maintainer's decision (2026-09-20): rustak becomes the OIDC provider CloudTAK talks to — it already federates to the real IdP behind `/oauth/authorize` — so the token CloudTAK ends up holding is rustak's own, which the enrolment routes already accept. rustak today has the authorization-code flow but no discovery document of its own, no JWKS, no ID token, no userinfo, and no client authentication (every client must use PKCE S256). This brief adds those, without changing one byte of the password grant CloudTAK uses today.

**Read first:** `.claude/plan/conventions.md`; `plan.md` → Identity & auth model, "Our JWT" decision (the 27-byte header is load-bearing: CloudTAK's hand parser needs it, see `compat/oauth.md` §2 — do not change the access-token header); `compat/oauth.md` (§1 and §4 corrections from M5-01); status M5-01 (the two authorization codes, `oauth_server/*` layout, the control/attack table in `auth/oauth_server/mod.rs`), M5-02 (scope claim as a *ceiling*: `tokens::scope_for`, `grants_admin`), M2-02/M2-08 (user rows carry an optional `email`, `identity/users.rs`), the OIDC account-linking commits (`abba577`, `ec7320f`, migration `0017_user_claims.sql`); `auth/jwt.rs` (where the RS256 key lives and how tokens are issued/verified), `auth/tokens.rs`, `auth/oauth_server/{authorize,codes,session,cookies}.rs`, `marti/oauth.rs` (the token endpoint), `marti/login.rs` (the route table), `config/auth.rs` (`OAuthClient`), `config/validate.rs`; `docs/deployment.md` "Browser single sign-on". For the relying-party shape you are serving, the TAK.NZ fork's `api/stateless/lib/oidc.ts` and the OIDC callback in `api/stateless/routes/login.ts` are summarised in the orchestrator's notes below — do not fetch or copy their code; the facts are enough.

**Facts about the client you are serving (from the fork; upstream will be the same shape or a standard library such as `openid-client`):** discovery must contain `authorization_endpoint`, `token_endpoint`, `userinfo_endpoint`; the authorize request carries `response_type=code`, `client_id`, `redirect_uri`, `scope` (default `openid profile email groups`), `state`, and **no** `code_challenge`; the token request is `application/x-www-form-urlencoded` with `grant_type=authorization_code`, `code`, `redirect_uri`, `client_id`, `client_secret`, expects JSON with `access_token` (and optionally `id_token`); userinfo is `GET` with `Authorization: Bearer <access_token>`, expects JSON with `preferred_username` and/or `email`, and `groups` as an array of strings; a standard library will additionally verify the ID token against `jwks_uri` (`iss`, `aud`, `exp`, `nonce`) and may use `client_secret_basic`.

**Deliver.**
1. **Discovery.** `GET /.well-known/openid-configuration` on the public listener (never Marti): `issuer` (= `[auth] issuer`, default the base URL — exactly the `iss` the tokens carry), `authorization_endpoint` (`/oauth/authorize`), `token_endpoint` (`/oauth/token`), `userinfo_endpoint` (`/oauth/userinfo`), `jwks_uri` (`/oauth/jwks`), `end_session_endpoint` (`/logout`), `response_types_supported: ["code"]`, `grant_types_supported: ["authorization_code","refresh_token","password"]`, `subject_types_supported: ["public"]`, `id_token_signing_alg_values_supported: ["RS256"]`, `scopes_supported: ["openid","profile","email","groups"]`, `token_endpoint_auth_methods_supported: ["client_secret_post","client_secret_basic","none"]`, `code_challenge_methods_supported: ["S256"]`, `claims_supported` (the claims below). Absolute URLs built from the issuer. Exact `Content-Type: application/json`. The existing `GET /login/.well-known/openid-configuration` (TAK's bare shape, the **upstream** provider's endpoints) stays exactly as it is — it answers a different question.
2. **JWKS.** `GET /oauth/jwks`: the RS256 public key(s) as a JWK set (`kty`, `n`, `e`, `alg: RS256`, `use: sig`, `kid`). The access-token header must stay the 27-byte `{"alg":"RS256","typ":"JWT"}` with no `kid`, so a verifier matches the key by algorithm; ID tokens are parsed by libraries, not by CloudTAK's hand parser, so they **may** carry `kid` in the header. Cacheable (`Cache-Control: public, max-age=3600`).
3. **Confidential clients.** `OAuthClient` gains `secret: Option<String>` (config value, `${{ env.X }}`-interpolated like `[auth.oidc] client_secret`; `Debug` redacts; never logged) and `post_logout_redirect_uris: Vec<String>` (default empty). `public = false` now **requires** `secret` and `public = true` **forbids** it — checked at `--check` with `Kind::User` advice. At `/oauth/token`, a confidential client must authenticate by `client_secret_post` or `client_secret_basic` (constant-time comparison; wrong or missing secret → `401 {"error":"invalid_client"}`); for a confidential client PKCE becomes **optional** (enforced when a `code_challenge` was sent, S256 only), for a public client it stays mandatory exactly as today. Update the control/attack table in `oauth_server/mod.rs` and the "Registering a client" docs accordingly.
4. **OpenID scopes on the authorize/code path.** `/oauth/authorize` reads `scope` and `nonce`; records the granted OIDC scopes (the intersection of the request with `openid profile email groups`) and the nonce on the code row (new migration — check the latest number — adding nullable `oidc_scope` and `nonce` columns to `oauth_codes`; never edit an applied migration). Keep the *rustak* scope ceiling logic untouched: the OIDC scopes are a separate string, not a substitute for `tokens::scope_for`. When the code is redeemed, the token response gains `id_token` (only when `openid` was granted) and `scope` (the granted OIDC scopes, space-separated) beside the existing `access_token`/`token_type`/`expires_in`(/refresh fields). The password grant response is **byte-for-byte unchanged** — assert that in a test.
5. **ID token.** RS256 JWT signed with the same key: `iss`, `sub` (the rustak username — the same `sub` the access token carries, so the identity CloudTAK sees in userinfo, the ID token and the certificate CN is one string), `aud` = the client id, `exp` (same lifetime as the access token), `iat`, `auth_time` (the session's creation time if known, else `iat`), `nonce` when one was sent, and the profile/email/groups claims below according to the granted scopes. Flat claims only (`groups` is a flat array of strings, which is allowed). 
6. **Userinfo.** `GET /oauth/userinfo` (also accept `POST`), Bearer only, any live rustak access token whose subject is an account: `sub` and `preferred_username` (both the username) always; `name` (display name if the account has one) and `email` (the account's `email` column when set, else omitted — never invent one) under `profile`/`email`; `groups` under `groups`: the names of the channels the account holds (IN or OUT, memberships not per-device state), plus a marker group for administrators whose name is `[auth.oauth] admin_group` (default `"admin"`) so a relying party can map admin rights by group. For a token issued by the password grant (no OIDC scopes recorded) release the full set — that token already had API scope over the same facts. Exact `Content-Type: application/json`; `401` with `WWW-Authenticate: Bearer` when the token is missing or bad.
7. **End session.** `GET|POST /logout` keeps its `204` behaviour when called bare; with `post_logout_redirect_uri` it answers `302` to that URI **only** if it is registered on the client named by `client_id` (or on any client when `id_token_hint`'s `aud` names one — keep it simple: require `client_id`), byte-for-byte match, else `204`. Preserve `state` on the redirect.
8. **Tests.** `rustak-server/tests/oidc_provider.rs` (`#![cfg(feature = "testing")]`) playing a generic relying party against the in-process server with `TestIdentityProvider` as the upstream: fetch discovery → build the authorize URL with `scope=openid profile email groups`, `state`, `nonce`, **no PKCE** → complete the upstream sign-in the way `oauth_flows.rs` does → get the code at the registered redirect → exchange with `client_secret_post` → verify the ID token against `/oauth/jwks` (`iss`, `aud`, `exp`, `nonce`, signature) → `userinfo` returns `sub`/`preferred_username`/`email`/`groups` as configured → **use the access token as Bearer on `GET /Marti/api/tls/config` and `POST /Marti/api/tls/signClient/v2`** and prove the mTLS `/Marti/api/version` probe succeeds with the issued certificate (this is the whole point: CloudTAK's enrolment path with a rustak token). Negatives: wrong secret → `invalid_client`; public client without PKCE still refused; confidential client that sent a `code_challenge` and a wrong verifier refused; `client_secret_basic` accepted; no `openid` scope → no `id_token`; `nonce` mismatch is the RP's job but the token must echo it exactly; userinfo without a token → `401`; `post_logout_redirect_uri` not registered → `204`; the password-grant response body has exactly the three keys it has today; `--check` refuses `public = false` without `secret` and `public = true` with one. Unit tests for the JWK encoding (`n`/`e` base64url, no padding) and the discovery document's URLs.
9. **Interop (cheap, do it if `interop/node-tak`'s harness makes it a one-file addition):** a scenario using the standard `openid-client` (current major, pinned) that performs discovery against the running server, fetches the JWKS, and calls `userinfo` with a token obtained through the existing password-grant scenario, asserting the claims — proving a real RP library consumes the documents. No browser sign-in in that suite (it has no upstream IdP), so the code exchange stays in the Rust test. Keep `surfaces.ts`/probe conventions (never probe POST-only paths; 404 or `text/html` = not served).
10. **Docs.** `docs/deployment.md`: a new subsection under "Browser single sign-on" — "rustak as CloudTAK's identity provider": the client block (`id`, `redirect_uris = ["https://<cloudtak>/api/login/oidc/callback"]`, `public = false`, `secret`, `post_logout_redirect_uris`), the CloudTAK-side values (Discovery URL `https://<rustak>/.well-known/openid-configuration`, client id/secret, scopes `openid profile email groups`), the claim mapping (`preferred_username` = rustak username; `email` only when the account has one; `groups` = channels + `admin`), and a plain note that upstream CloudTAK has not shipped its relying-party back end yet (issue #661) so this is ready for it, not usable with a stock CloudTAK today. `config.example.toml` `[auth.oauth]` block (`secret`, `post_logout_redirect_uris`, `admin_group`). `compat/oauth.md`: a §5 "rustak as an OpenID provider" with the exact documents.

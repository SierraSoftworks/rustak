# M6-01 — Services control API, server-event feed, and the sidecar SDK's enrolment and Marti client

**Read first:** `.claude/plan/conventions.md`; `plan.md` → "Plugin (sidecar) contract" and Milestones M6; `docs/plugins.md`; status `M1-07-sidecar-stream-wiring.md` (harness, `Sidecar` trait, `Link`), `M0-15-plugin-example.md`, `M2-02-identity-credentials.md` (`ServiceToken`, service users), `M2-03-enrollment-endpoints.md` (`signClient/v2` contract, Basic with enrolment token), `M3-01`/`M3-02`/`M4-01` status files for the Marti surfaces the client wraps; `rustak-client/src/{sidecar,stream}/**`.

**Deliver.**
1. **Server** (`rustak-server/src/plugins/{registry,health,events}.rs`, `web/api/services.rs`, `web/api/events.rs`, migration `0014` if `services` needs columns): `POST /api/v1/services/register` (service-token or service-cert auth; upsert `{name, version, capabilities, endpoint?}`), `POST /api/v1/services/{name}/heartbeat {status, detail}`, `GET /api/v1/services` (admin: name, user, last heartbeat, status), `DELETE /api/v1/services/{name}`, per-service config KV `GET/PUT /api/v1/services/{name}/config` (JSON object, admin writes, the service reads its own), and `GET /api/v1/events` — Server-Sent Events (`actix-web` streaming response, `Last-Event-ID` resume from a bounded ring buffer) carrying `client.connected`, `client.disconnected`, `mission.changed`, `channel.changed`, `package.uploaded`, `service.status` from a `broadcast` bus fed by `stream::LiveState` hooks, the mission notifier, `identity::members` and `files::upload`. Service identities are `UserKind::Service` users; a service token is minted like any credential.
2. **SDK** (`rustak-client/src/{enroll.rs, marti/{mod,client,missions,files,groups,contacts}.rs, control/{mod,register,events}.rs}`): `enroll` (CSR → `signClient/v2` with an enrolment token, PKCS#8 key kept locally, truststore from `tls/config`/CA download), a typed Marti client over `reqwest` (rustls, client cert) for missions (create/get/subscribe/contents/changes/logs), files (upload/search/download), groups and contacts, mission tokens; a control client (register, heartbeat loop, config fetch, SSE consumer as a `Stream<Item = ServerEvent>`); the `Sidecar` harness gains `SidecarContext` handles for all three so `on_event`/`tick` can call them, plus automatic registration + heartbeat when `[service]` is configured.
3. **Example**: `rustak-plugin-example` registers itself, publishes its heartbeat SA, and logs `client.connected` events from the feed; `docs/plugins.md` gains "Registering with the server" and "Reacting to server events", and the copy-and-rename recipe is checked end to end (`cargo new` steps).
4. Tests: server route tests (authz: only the service or an admin may write its config; SSE resume), an in-process integration test in `rustak-server/tests/services_flow.rs` that runs the example plugin's harness against a `TestServer` + the stream listener (enrol → connect → register → heartbeat → event received), SDK unit tests with `wiremock`.

# M9-11 — Control-link polish from the first working deployment

**Why — production findings, 2026-09-22 (Dublin, images at `480272d`).** The control link now works end to end (workload identity exchanged at `/oauth/token`, registered, event feed open, zero errors). Four things remain, in the operator's order of importance; the operator retired a previous TAK server partly for log noise.

1. **The server-event feed reopens every ~31 s.** Both sidecars log "The server-event feed is open." at 00:13:06, 00:13:37, 00:14:08, … `rustak-client/src/http.rs:165` builds the control client with `.timeout(DEFAULT_TIMEOUT)` (30 s) — reqwest's *total* request timeout — and `control/events.rs` reads the SSE body through that same client, so every stream is cut at 30 s. Each reopen costs a `/oauth/token` and/or `/api/v1/events` request that rustak logs at INFO with the full request span: 74 rustak log lines in 2.5 minutes from two idle sidecars.
2. **The second Identity line is wrong prose**: `Identity: this sidecar is 'the control API', from NOMAD_TOKEN_rustak. … account="the control API"` (`sidecar/workload.rs:244`, called with `"the control API"` at `:325`). It means the sidecar is authenticating *to* the control API *as its own account* with the workload identity. It is also logged twice (once outside and once inside the `sidecar{…}` span).
3. **The first batch is thrown away with a false WARN on every clean start**: `WARN link: Discarding events: the CoT stream is reconnecting. count=17` (`sidecar/link.rs:138`) — the first poll's result is published ~40 ms before the stream's first connect completes. Harmless (the next tick republishes) but it is a WARN on every start and it calls a first connection a reconnection.
4. (No code here.) adsb.lol answers `Retry-After: 20` about once a minute even at `poll = "10s"`; M9-08's adaptive cadence (landed `7a8b6a4`) is expected to absorb it.

**Deliver.**
1. **A long-lived feed with no total timeout.** The SSE request uses a client (or a per-request override) with a connect timeout and **no total timeout**; liveness comes from an *idle* timeout on the body — if the server sends SSE keep-alive comments (check `web/api/events.rs`; if it does not, add them every 15 s, which also keeps proxies from idling the connection out), treat ~3 missed keep-alives as a dead feed and reconnect through `link_health`'s backoff. Ordinary calls keep their 30 s total timeout. The access token obtained by the workload exchange is reused across reopenings until 60 s before expiry (M9-06 says it is cached — verify a reopen does not force a new exchange).
2. **Quiet reopening.** "The server-event feed is open." is `info` the first time and after an outage that `link_health` reported; a clean server-side close followed by a successful reopen is `debug`. A feed that closes cleanly more than, say, 5 times in 5 minutes gets one counted reminder at `warn` (something is cutting it), in `link_health`'s style.
3. **Server: routine success is not INFO.** In `web/telemetry.rs`, find what is emitted per request. Successful (2xx/3xx) requests must not produce an `info` *event*; keep the span for tracing/OTel export, log 4xx at `debug` (or `info` for 401/403 on credential endpoints if that is the existing security posture — check R-01's notes and keep audit trails intact; the audit log is separate and must not change), 5xx at `error`/`warn` as today. State exactly what changed and what an operator sees at `LOG_LEVEL=info` for an idle server with two sidecars: the target is zero lines per minute.
4. **Identity line.** Reword to one line per credential actually used, e.g. `Identity: this sidecar is 'adsb', from the certificate at '/data/adsb.pem'.` (unchanged) and `Identity: authenticating to the control API as 'adsb' with the workload identity from NOMAD_TOKEN_rustak. issuer=… account="adsb"` — the account is the real account (from the exchanged token's `sub` or the configured account), never a description. Logged once.
5. **First connect.** The harness holds the first drain until the stream's first connect completes, bounded (e.g. 10 s, then proceed and let the normal path handle it); `link.rs` distinguishes "never yet connected" from "reconnecting": before the first connection it says nothing at `warn` (one `debug`), and the discard WARN is reserved for a stream that was up and dropped — logged on state change, not per tick, with a count in the reminder. Feed plugins' first batch must reach the stream on a clean start (assert it in the harness).
6. **Tests.** Client: an SSE response held open for longer than the old total timeout (use a short test timeout constant injected into the client builder rather than sleeping 30 s) stays open; idle detection fires when keep-alives stop; a clean close + reopen logs through the quiet path (assert on the state machine, not log capture); the token is not re-exchanged on reopen. Server: a test on the request-logging decision function (status → level). Harness (`rustak-server/tests/feed_sidecars.rs`): the first replayed batch arrives with no discard on a clean start. Identity line: unit test on the rendered text for both credentials.
7. **Docs.** `docs/plugins.md` (the feed is long-lived; what the control link logs and when), `docs/deployment.md` "Logging and telemetry" (what `LOG_LEVEL=info` shows for routine traffic after this change; a reverse proxy in front of `[web.public]` must not buffer or idle out `text/event-stream` — name the keep-alive interval).
